# Telegram Catalog MVP

Каталог товаров с Telegram Mini App. Администратор отправляет боту одну фотографию с названием в подписи; покупатель открывает каталог, добавляет товары в корзину и оформляет заказ.

Товар содержит название и фотографию. Заказ сохраняет идентификатор, владельца, дату, названия и количества. Цены, оплата, остатки, доставка и контактные данные не предусмотрены.

## Демо

- [Telegram-бот](https://t.me/dasferwer_catalog_753864_bot)
- [Веб-каталог](https://tutor-diminish-hermit.ngrok-free.dev)

Демо доступно, пока работают компьютер, Docker и туннель. При первом открытии бесплатный ngrok может показать страницу с кнопкой **Visit Site**; после перехода открывается каталог. Адрес закреплён за аккаунтом, но доступность зависит от работающего стенда и [лимитов бесплатного тарифа](https://ngrok.com/docs/pricing-limits/free-plan-limits).

## Требования и готовность

Next.js 16 App Router / TypeScript, FastAPI, aiogram 3.x, PostgreSQL 17, MinIO через S3 API. Python 3.13 и Node.js 24; зависимости закреплены в `backend/uv.lock`, `frontend/package-lock.json` и Go lock-файлах. Базовые Docker-образы закреплены digest.

Для запуска нужен Docker Compose v2+, доступ к интернету при сборке и свободный порт 8088. Первая сборка MinIO компилирует закреплённый исходный код и может занять несколько минут. Для проверок на хосте нужны Python, `uv` и npm.

## Запуск без настоящего Telegram

```sh
python3 scripts/configure.py
docker compose -f compose.yml -f compose.test.yml build
docker compose -f compose.yml -f compose.test.yml up -d --wait --scale web=2 --scale api=2 --scale bot=2
docker compose -f compose.yml -f compose.test.yml run --rm --no-deps tests
```

Откройте <http://localhost:8088>. Последняя команда выполняет интеграционные проверки и создаёт тестовые товары. Она не очищает существующие данные. Без неё новый каталог пуст.

`compose.test.yml` подключает внутренний тестовый Telegram API с фиктивным токеном и администратором 42. Настоящему Telegram сообщения не отправляются. Фотографии и API доступны через один origin; порты PostgreSQL и MinIO на хост не опубликованы.

`configure.py` создаёт `.env` с правами `0600` и раздельными случайными паролями, не перезаписывая существующий файл. Секретный `.env` не входит в репозиторий. При конфликте порта или подсети измените `HTTP_PORT`, `PUBLIC_ORIGIN` и `COMPOSE_SUBNET`.

## Настоящий бот и HTTPS

1. Создайте отдельного тестового бота через BotFather и получите числовые Telegram ID администраторов.
2. Подготовьте доступный Telegram и браузеру HTTPS origin. Reverse proxy должен направлять все запросы на gateway, сохраняя `/api/*` и `/telegram/webhook`.
3. Заполните локальный `.env`: `BOT_TOKEN`, `ADMIN_IDS`, случайный `WEBHOOK_SECRET`, `PUBLIC_ORIGIN=https://…`, `COOKIE_SECURE=true`.
4. Запустите стенд и отдельно зарегистрируйте webhook:

```sh
docker compose up -d --wait --build --scale web=2 --scale api=2 --scale bot=2
docker compose run --rm --no-deps bot python -m shop.webhook
```

Для настоящего бота не подключайте `compose.test.yml`. Команда регистрации отказывается заменять существующий webhook. Флаг `--replace-existing` используйте только после проверки действующей интеграции своего бота. Pending updates сохраняются; запуск и остановка реплик webhook не меняют.

Публичное демо должно оставаться доступным на время проверки. При локальном туннеле компьютер, Docker и процесс туннеля должны работать постоянно. После смены адреса обновите `PUBLIC_ORIGIN`, перезапустите API/бота, замените webhook своего тестового бота и получите новую кнопку через `/start`: старые сообщения сохраняют старую ссылку.

| Переменная | Назначение |
|---|---|
| `HTTP_PORT`, `COMPOSE_SUBNET` | Локальный порт gateway и подсеть Compose; по умолчанию 8088 и `10.247.88.0/24` |
| `PUBLIC_ORIGIN`, `COOKIE_SECURE` | Внешний origin без пути и безопасные cookies; для HTTPS обязательно `true` |
| `BOT_TOKEN` | Секретный токен отдельного тестового бота |
| `ADMIN_IDS` | Положительные числовые Telegram ID через запятую |
| `WEBHOOK_SECRET` | Случайная строка 1–256 символов `A-Z a-z 0-9 _ -` |
| `POSTGRES_PASSWORD`, `APP_DATABASE_PASSWORD` | Раздельные пароли администратора PostgreSQL и роли приложения |
| `S3_ROOT_USER`, `S3_ROOT_PASSWORD` | Административные реквизиты MinIO для инициализации |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Отдельные реквизиты приложения с ограниченной политикой S3 |

### Пользовательский сценарий

В личном чате `/start` и обычное обращение вне административного сценария возвращают точную фразу «У меня есть товар» и кнопку «Открыть каталог».

Администратор вызывает `/create_product` или нажимает «Создать товар», затем отправляет **одно сообщение photo + caption**. Название берётся из подписи после trim. Приглашение и подсказки об ошибках приходят без кнопок; после успешного сохранения кнопки возвращаются. Кнопки старых сообщений остаются в истории.

Каталог открывается внутри Telegram через `InlineKeyboardButton.web_app`. Обычный браузер работает без Telegram SDK и использует независимую гостевую корзину. Откройте карточку, добавьте товар, измените количество, оформите заказ и обновите подтверждение: состав и идентификатор сохраняются, корзина очищена. Объединение гостевой и Telegram-корзин не предусмотрено.

## Архитектура и данные

| Модули | Ответственность |
|---|---|
| `frontend/app`, `components`, `lib` | App Router, каталог/карточка/корзина/заказ, клиентская сессия и HTTP |
| `backend/shop/api.py`, `bot.py` | Раздельные HTTP entrypoint API и aiogram webhook |
| `cart.py`, `bot_logic.py` | Бизнес-операции корзины/заказа и административного диалога |
| `models.py`, `db.py`, `migrations` | PostgreSQL, независимые AsyncSession и миграции |
| `storage.py`, `security.py` | Ограниченный S3 I/O, проверка изображений и подписи Telegram |
| `infra/haproxy.cfg` | Round-robin, readiness и повторное обнаружение реплик через Docker DNS |

В PostgreSQL находятся товары, владельцы, сессии, корзины, снимки заказов, административное состояние и обработанные update ID. В MinIO хранятся фотографии; в таблице товара — ключ объекта и метаданные. Приватный bucket читается через API: браузер не получает внутренний Docker-адрес или Telegram-ссылку с токеном.

Cookie содержит случайный 256-битный токен, в БД хранится его SHA-256. Срок гостевой сессии — 30 суток, Telegram — сутки. Для HTTPS cookie имеет HttpOnly, Secure, `__Host-`, SameSite=None и Partitioned; локальный HTTP использует SameSite=Lax. Вложенному Telegram Web нужен браузер с поддержкой CHIPS, включая Safari 18.4+.

Изменяющие запросы требуют точный Origin и CSRF. Владелец определяется серверной сессией; чужой заказ возвращает 404. Заголовок `X-Checkout-Scope` только сверяет ожидаемого владельца и не предоставляет доступ. Telegram initData проверяется HMAC-SHA-256 с безопасным сравнением, уникальностью полей и давностью 0–3600 секунд. Неверная переданная авторизация не включает гостевой режим.

Повторный Telegram-вход того же владельца сохраняет действующую сессию. При первом гостевом входе без Web Locks согласование допустимо только для новой локально неиспользованной вкладки при чтении корзины: до попыток записи, чтения непустой/изменённой корзины и незавершённого checkout. Проверки повторяются после ожидания сети. Операции и ключи checkout между владельцами не переносятся; восстановление доступа к прежнему гостю после потери cookie не обещается.

### Stateless и конкурентность

Web, API и bot запускаются минимум в двух репликах из одинаковых образов внутри каждой группы. У приложений read-only filesystem, нет writable-томов, tmpfs, локального FSM, sticky sessions или process-local дедупликации. PostgreSQL и MinIO имеют постоянные тома и являются общими хранилищами для всех реплик.

Next.js использует динамический SSR и `cache: no-store`; нет ISR, кеша пользовательских данных или runtime-кеша оптимизатора изображений. Фотографии выводятся обычным `img`. Синхронный S3-клиент работает в отдельном ограниченном пуле потоков; файлы не записываются на диск приложений.

Все изменения корзины и checkout блокируют строку владельца `FOR UPDATE` и проверяют версию. Устаревший конкурентный запрос получает 409. Снимок заказа и очистка корзины фиксируются одной транзакцией. Уникальность `(owner_id, idempotency_key)` возвращает сохранённый заказ при повторе; несовместимая версия с тем же ключом даёт 409. Клиент сохраняет ключ/версию попытки в `sessionStorage` по серверному scope владельца и использует их после потери ответа и reload.

Aiogram FSM отключён; ожидание photo + caption находится в PostgreSQL. Уникальная вставка `(bot_id, update_id)` сериализует повторы, административная строка блокируется в БД. Товар и переход состояния фиксируются вместе. Webhook проверяет секрет и **дожидается** `feed_update`; временная ошибка даёт 503, раннего фонового 2xx нет.

### Сбои и границы гарантий

PostgreSQL и S3 не имеют общей транзакции. Сначала загружается объект, затем фиксируется товар. Ключ содержит bot ID, update ID и SHA-256 фотографии; повтор использует тот же объект. Компенсационное удаление не выполняется, чтобы не удалить фото другого успешного commit. После аварии до commit возможен неподключённый объект.

Для ручной очистки остановите приём webhook и все bot-реплики, дождитесь завершения запросов/транзакций, сохраните возможность повторной доставки и сопоставьте bucket с `products.object_key`. Удаляйте только неиспользуемые ключи после проверки; повторная обработка загрузит объект заново. Очистка не должна идти одновременно с загрузками.

Подтверждение бота отправляется после commit; ответ и статус доставки сохранены в `bot_updates`. При ошибке отправки повтор webhook возвращается к сохранённому ответу без нового товара. Сбой после отправки до фиксации статуса может дать повторное сообщение: exactly-once для внешних сообщений не гарантируется. После прекращения повторов Telegram оператор может повторно подать исходное обновление в защищённый webhook.

Остановка отдельной реплики может оборвать её текущий запрос; после обновления health-check оставшаяся обслуживает повторы. Локальный Compose не обеспечивает HA общих PostgreSQL, MinIO и gateway. Для HA всего сервиса нужны PostgreSQL с управляемыми репликацией/failover, распределённый MinIO и несколько ingress-экземпляров.

### Лимиты

Название — 1–200 символов после trim; одна JPEG/PNG до 5 МиБ и 16 Мп; альбомы отклоняются. Количество — 1–99, до 100 разных позиций, каталог по 20 товаров. HTTP body — до 64 КиБ.

Webhook — 40 секунд и 4 обработки на реплику; Telegram API — 10 секунд. S3 — connect 2/read 5 секунд, максимум 2 попытки и 4 операции на процесс; отмена запроса не освобождает слот до завершения I/O. DB pool — 3 соединения без overflow на Python-реплику: две API и две bot используют максимум 12 постоянных соединений. Клиенты и пулы закрываются при остановке.

## Миграции и обновления

Compose выполняет одноразовые `migrate`, `database-init`, `storage-init` перед запуском реплик. Миграции не запускаются параллельно каждым worker. Создаются роль `catalog_app` без DDL, приватный bucket и S3-пользователь с чтением bucket и записью только `products/*`, без удаления/администрирования. Административные пароли приложениям не передаются.

Повторная инициализация безопасна. При необходимости её можно выполнить отдельно на уже работающих хранилищах:

```sh
docker compose run --rm --no-deps migrate
docker compose run --rm --no-deps database-init
docker compose run --rm --no-deps storage-init
```

Повторный `up` сохраняет данные; удаление томов не требуется. Для существующего PostgreSQL-тома изменение `POSTGRES_PASSWORD` не меняет пароль в БД: используйте защищённое административное подключение и `\password catalog`, затем обновите конфигурацию. Пароли роли приложения и S3 обновляются повторной инициализацией; root-пароль MinIO — конфигурацией и перезапуском хранилища.

При смене базовой ОС PostgreSQL проверьте `datcollversion` и `pg_database_collation_actual_version(oid)`. Для несовпадения выполните `REINDEX DATABASE catalog` вне транзакции, затем `ALTER DATABASE catalog REFRESH COLLATION VERSION`; остальные используемые БД проверяются отдельно.

## Проверки

Используйте отдельный тестовый стенд с `compose.test.yml`: runtime-проверки останавливают и возвращают его реплики и зависимости. Они отказываются работать без тестового Telegram API и не удаляют тома. Проверки границ commit временно устанавливают PostgreSQL-триггеры и снимают их после сценария.

```sh
npm --prefix frontend ci
(cd frontend && npx playwright install chromium)
scripts/check.sh
```

Полный скрипт выполняет Ruff/format, strict mypy, тесты подписи, TypeScript, production build, сборку Compose, запуск двух реплик, интеграционные тесты, проверки отказов и Chromium E2E. Для проверки зависимостей после установки Trivy: `scripts/check-security.sh`; подробности и остаточные предупреждения — [SECURITY.md](SECURITY.md).

Проверены локально: **59 Python-тестов** с настоящими PostgreSQL/MinIO и тестовым Telegram API, **27 Chromium E2E**, чистые миграции, повторная инициализация и остановка/возврат реплик web/API/bot. Проверены межрепличные дубли, kill до/после commit, отказы хранилищ, права, подписи, изоляция, гонки корзины и повторы checkout. Идентификаторы экземпляров видны в `X-Instance-ID`, `X-Upstream` и web `/health`.

Реальный сценарий создания товара, каталога, корзины и заказа проверен вручную в Telegram для macOS. Telegram identity/SDK в автоматических E2E заменены контролируемыми тестовыми данными. Проверки не являются испытанием production-нагрузки, HA хранилищ или всех клиентов Telegram.
