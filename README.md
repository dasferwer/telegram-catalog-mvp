# Telegram Catalog MVP

Магазин с каталогом в браузере и Telegram Mini App. Администратор добавляет товар через бота: отправляет фотографию и название в подписи одним сообщением. Покупатель открывает карточку, добавляет товар в корзину и оформляет заказ.

У товара есть название и фотография. Заказ сохраняет владельца, дату, идентификатор, названия товаров и количества. Цены, оплата, остатки, доставка и контакты покупателя в задании не предусмотрены.

## Демо

- [Telegram-бот](https://t.me/dasferwer_catalog_753864_bot)
- [Каталог](https://catalog.176.109.111.18.sslip.io)

Стенд работает на отдельной ВМ и не зависит от локального компьютера. HTTPS обслуживает Caddy. Плановое отключение ВМ — 15 ноября 2026 года в 09:15 по Москве.

В этой сети Telegram не подключается к webhook напрямую, поэтому для него используется Cloudflare Quick Tunnel на той же ВМ. Каталог, API и фотографии доступны по одному адресу. После пересоздания туннеля его адрес меняется: webhook нужно зарегистрировать заново, сохранив ожидающие обновления. Постоянная работа временного туннеля не гарантируется.

## Требования и готовность

Стек: Next.js 16 App Router, TypeScript, FastAPI, aiogram 3.x, PostgreSQL 17 и MinIO. Python 3.13, Node.js 24. Зависимости закреплены в `backend/uv.lock`, `frontend/package-lock.json` и Go lock-файлах; Docker-образы — по digest.

Реализованы создание товара, каталог, карточка, корзина и заказ без оплаты. Web, API и bot запускаются в двух репликах. Для сборки нужны Docker Compose v2+, интернет и свободный порт 8088. Первая сборка MinIO из исходного кода занимает несколько минут.

## Локальный запуск

```sh
python3 scripts/configure.py
docker compose -f compose.yml -f compose.test.yml build
docker compose -f compose.yml -f compose.test.yml up -d --wait --scale web=2 --scale api=2 --scale bot=2
docker compose -f compose.yml -f compose.test.yml run --rm --no-deps tests
```

Каталог: <http://localhost:8088>. Последняя команда запускает интеграционные тесты и добавляет тестовые товары. Без неё новый каталог пуст. Существующие данные не удаляются.

`compose.test.yml` подключает тестовый Telegram API с фиктивным токеном и администратором 42. Сообщения в настоящий Telegram не отправляются. Порты PostgreSQL и MinIO на хост не опубликованы.

`configure.py` создаёт `.env` с отдельными случайными паролями и правами `0600`. Существующий файл не перезаписывается, секреты в репозиторий не входят. Если порт или подсеть заняты, измените `HTTP_PORT`, `PUBLIC_ORIGIN` и `COMPOSE_SUBNET`.

## Настройка настоящего бота

1. Создайте тестового бота через BotFather и получите числовые Telegram ID администраторов.
2. Подготовьте HTTPS-адрес, доступный Telegram и браузеру. Reverse proxy должен передавать запросы в gateway, сохраняя пути `/api/*` и `/telegram/webhook`.
3. Заполните `.env`: `BOT_TOKEN`, `ADMIN_IDS`, случайный `WEBHOOK_SECRET`, `PUBLIC_ORIGIN=https://…`, `COOKIE_SECURE=true`.
4. Запустите стенд без `compose.test.yml` и зарегистрируйте webhook отдельной командой:

```sh
docker compose up -d --wait --build --scale web=2 --scale api=2 --scale bot=2
docker compose run --rm --no-deps bot python -m shop.webhook
```

Команда не заменяет существующий webhook без флага `--replace-existing`. Используйте его только для своего тестового бота после проверки текущего адреса. Ожидающие обновления сохраняются. При старте и остановке реплик webhook не меняется.

Если для webhook нужен отдельный адрес, передайте `PUBLIC_ORIGIN` только команде регистрации:

```sh
docker compose run --rm --no-deps -e PUBLIC_ORIGIN=https://webhook.example.com bot python -m shop.webhook --replace-existing
```

У работающих API и bot оставьте `PUBLIC_ORIGIN` каталога. Для работы бота нужен доступ к `api.telegram.org` по HTTPS; проверка TLS-сертификата должна оставаться включённой.

После смены адреса каталога обновите `PUBLIC_ORIGIN`, перезапустите API и bot и отправьте `/start`: кнопки старых сообщений сохраняют прежнюю ссылку.

| Переменная | Назначение |
|---|---|
| `HTTP_PORT`, `COMPOSE_SUBNET` | Порт gateway и подсеть; по умолчанию 8088 и `10.247.88.0/24` |
| `PUBLIC_ORIGIN`, `COOKIE_SECURE` | Адрес каталога без пути; для HTTPS обязательно `COOKIE_SECURE=true` |
| `BOT_TOKEN` | Токен тестового бота |
| `ADMIN_IDS` | Числовые Telegram ID администраторов через запятую |
| `WEBHOOK_SECRET` | Случайная строка 1–256 символов из `A-Z a-z 0-9 _ -` |
| `POSTGRES_PASSWORD`, `APP_DATABASE_PASSWORD` | Отдельные пароли администратора БД и роли приложения |
| `S3_ROOT_USER`, `S3_ROOT_PASSWORD` | Реквизиты администратора MinIO для инициализации |
| `S3_ACCESS_KEY`, `S3_SECRET_KEY` | Реквизиты приложения с ограниченными правами S3 |

## Сценарий работы

На `/start` и обычное сообщение вне добавления товара бот отвечает «У меня есть товар» и показывает кнопку «Открыть каталог».

Администратор вызывает `/create_product` или нажимает «Создать товар», затем отправляет одну фотографию с названием в подписи. Пробелы по краям названия удаляются. Подсказки приходят без кнопок; после сохранения товара кнопки возвращаются. Кнопки старых сообщений остаются в истории.

Каталог работает в обычном браузере без Telegram SDK и открывается внутри Telegram через `web_app`. Гостевая и Telegram-корзины независимы. В корзине можно изменить количество и удалить товар. После оформления показываются сохранённый состав и идентификатор заказа; корзина очищается.

## Архитектура

| Файлы | Назначение |
|---|---|
| `frontend/app`, `components`, `lib` | Страницы, клиентская сессия и запросы к API |
| `backend/shop/api.py`, `bot.py` | FastAPI и webhook aiogram |
| `cart.py`, `bot_logic.py` | Операции корзины, заказа и добавления товара |
| `models.py`, `db.py`, `migrations` | Модели PostgreSQL, соединения и миграции |
| `storage.py`, `security.py` | Работа с S3 и проверка Telegram initData |
| `infra/haproxy.cfg` | Балансировка, проверки готовности и обнаружение реплик через Docker DNS |

PostgreSQL хранит товары, владельцев, сессии, корзины, заказы, состояние диалога и обработанные обновления бота. Фотографии находятся в приватном bucket MinIO. В товаре хранится ключ объекта, изображение выдаёт API. Внутренние адреса Docker и Telegram-ссылки с токеном в браузер не передаются.

Web, API и bot не хранят изменяемые данные на диске. Файловая система приложений доступна только для чтения, writable-томов и tmpfs нет. У всех реплик общие PostgreSQL и MinIO с постоянными томами. Локального FSM, sticky sessions и дедупликации в памяти процесса нет.

Next.js получает данные без кеширования (`cache: no-store`), не использует ISR и выводит фотографии обычным `img`. Синхронный S3-клиент работает в ограниченном пуле потоков. Фотографии не записываются во временные файлы приложений.

### Сессии и доступ

В HttpOnly cookie передаётся случайный 256-битный токен, в БД хранится его SHA-256. Гостевая сессия действует 30 суток, Telegram-сессия — сутки. Для HTTPS используются Secure, `__Host-`, SameSite=None и Partitioned; для локального HTTP — SameSite=Lax. В Telegram Web нужен браузер с поддержкой CHIPS, включая Safari 18.4+.

Изменяющие запросы проверяют Origin, CSRF и владельца сессии. Чужой заказ возвращает 404. Telegram initData проверяется по HMAC-SHA-256 с безопасным сравнением подписей, проверкой полей и давностью до часа. Неверная Telegram-авторизация отклоняется.

Повторный вход того же Telegram-пользователя сохраняет сессию. При одновременном первом гостевом входе без Web Locks новая вкладка может согласовать сессию при чтении пустой корзины, пока в ней не было записи или попытки оформления. После начала работы с корзиной менять владельца автоматически нельзя. Восстановление гостевой корзины после потери cookie не предусмотрено.

### Транзакции и повторы

Изменения корзины и оформление блокируют строку владельца через `FOR UPDATE` и проверяют версию. Устаревший запрос получает 409. Заказ и очистка корзины сохраняются одной транзакцией.

Уникальность `(owner_id, idempotency_key)` защищает от повторного заказа. Повтор возвращает сохранённый результат; тот же ключ с другой версией корзины даёт 409. Клиент сохраняет ключ и версию попытки в `sessionStorage` отдельно для каждого владельца.

Состояние ожидания фото хранится в PostgreSQL. Уникальность `(bot_id, update_id)` защищает от повторной обработки обновления. Товар и состояние диалога фиксируются вместе. Webhook проверяет секрет и ждёт завершения обработки; временный сбой возвращает 503.

Сначала фотография загружается в S3, затем сохраняется товар. Общей транзакции между S3 и PostgreSQL нет. Ключ объекта включает bot ID, update ID и SHA-256 фотографии. Повтор использует тот же ключ. После аварии до commit может остаться объект без товара; автоматическое удаление не выполняется.

Для ручной очистки остановите приём webhook и все bot-реплики, дождитесь завершения запросов и сопоставьте объекты с `products.object_key`. Удаляйте только неиспользуемые ключи после проверки, сохраняя возможность повторной доставки обновлений. Не запускайте очистку одновременно с загрузками.

Ответ бота отправляется после commit. Его содержимое и статус доставки находятся в `bot_updates`. Ошибка отправки не создаёт товар повторно. Если процесс остановится после отправки, но до сохранения статуса, ответ может прийти ещё раз. Если Telegram прекратил повторы, оператор может повторно передать исходное обновление в защищённый webhook.

Оставшаяся реплика обслуживает запросы после исключения недоступной из балансировки. Одна ВМ, общий PostgreSQL, MinIO и gateway остаются точками отказа стенда. Для HA нужны репликация и failover PostgreSQL, распределённый MinIO и несколько ingress-экземпляров.

## Лимиты

Название — 1–200 символов, фотография — JPEG/PNG до 5 МиБ и 16 Мп. Альбомы отклоняются. Количество — 1–99, до 100 позиций в корзине, по 20 товаров на страницу. Тело HTTP-запроса — до 64 КиБ.

На bot-реплику допускается 4 обработки webhook с таймаутом 40 секунд. Telegram API — 10 секунд. S3 — таймаут соединения 2 секунды, чтения 5 секунд, до 2 попыток и 4 операций на процесс. Отмена запроса не освобождает слот до завершения I/O.

Пул БД — 3 соединения без overflow на Python-реплику: две API и две bot используют до 12 постоянных соединений. При остановке соединения и клиенты закрываются.

## Миграции и обновления

Перед репликами Compose выполняет одноразовые `migrate`, `database-init` и `storage-init`. Создаются таблицы, роль `catalog_app` без DDL, приватный bucket и S3-пользователь с чтением bucket и записью только в `products/*`. Административные реквизиты приложениям не передаются.

Повторная инициализация сохраняет данные. На работающих хранилищах её можно выполнить отдельно:

```sh
docker compose run --rm --no-deps migrate
docker compose run --rm --no-deps database-init
docker compose run --rm --no-deps storage-init
```

Изменение `POSTGRES_PASSWORD` в окружении не меняет пароль существующей БД. Сначала смените его через защищённое административное подключение командой `\password catalog`, затем обновите конфигурацию. Пароль роли приложения и реквизиты S3 обновляются повторной инициализацией; root-пароль MinIO — конфигурацией и перезапуском хранилища.

При смене базовой ОС PostgreSQL проверьте `datcollversion` и `pg_database_collation_actual_version(oid)`. Если версии различаются, выполните `REINDEX DATABASE catalog` вне транзакции, затем `ALTER DATABASE catalog REFRESH COLLATION VERSION`. Остальные используемые БД проверяются отдельно.

## Проверки

Проверки отказов запускаются только на отдельном стенде с `compose.test.yml`. Они останавливают и возвращают реплики и хранилища, не удаляя тома. Без тестового Telegram API скрипт отказывается работать. Тесты границ commit временно устанавливают PostgreSQL-триггеры и удаляют их после сценария.

```sh
npm --prefix frontend ci
(cd frontend && npx playwright install chromium)
scripts/check.sh
```

Скрипт выполняет Ruff, проверку форматирования, strict mypy, TypeScript, production build, запуск двух реплик, интеграционные тесты, проверки отказов и Chromium E2E. Проверка зависимостей с установленным Trivy: `scripts/check-security.sh`. Результаты проверки зависимостей и оставшиеся предупреждения описаны в [SECURITY.md](SECURITY.md).

Локально выполнены 59 Python-тестов с PostgreSQL, MinIO и тестовым Telegram API, 27 Chromium E2E, чистые миграции, повторная инициализация и остановка/возврат реплик. Проверялись дубли обновлений, остановка процесса до и после commit, отказы хранилищ, права, подписи, изоляция пользователей и гонки корзины. Экземпляры видны в `X-Instance-ID`, `X-Upstream` и `/health` фронтенда.

На демо-сервере запущены две реплики web, API и bot. Проверены HTTPS, фотографии, гостевая корзина, сохранённый заказ и повтор оформления с тем же ключом. Каталог, корзина и заказ на текущем адресе проверены вручную внутри Telegram. Автоматические тесты Telegram используют контролируемый адаптер и не заменяют проверку в настоящем клиенте. Нагрузочное тестирование и отказоустойчивость самих хранилищ не проверялись.
